# Real-data validation plan: Rossi (TVC) + EBMT4 (CR + TVC)

Branch `feat/rc-validation`. Parent: user request 2026-09-27, before the release-readiness pass ("test on more real-life data for more robust testing before release candidate"). Not a `tvc-plan.md` slice (S16-S20 is closed); this is pre-release validation, its own plan. Follows the two existing case-study data conventions exactly (`examples/data/cunningham_lemke.py`'s checksum-verified download-on-demand vs `tests/fixtures/pbcseq.py`'s committed CSV fixture), picking between them per-dataset on licence grounds (Decision 1).

## Why these two, not more
Picked from a wider domain search (political science leader tenure, business/reliability, ecology were also found but need heavier reshaping or aren't public-domain in a ready shape — see prior turn). Rossi and EBMT4 were chosen because they exercise the two real-data code paths S16-S20 has never run against real data: a genuine time-varying covariate on a single-event counting-process fit (Rossi), and a genuine competing-risks fit with a time-varying covariate (EBMT4) — `pbc2`'s case study already covers landmark + counting-process on real longitudinal biomarkers, and `btscs` covers a real single-event TVC fit without competing risks, so neither existing case study touches `CompetingRisksForestTV` on real data at all.

## Decisions

1. **Data sourcing and licence handling.**
   - **Rossi**: source is `carData` (CRAN, GPL >= 2), the same licence class as `survival` (whose `pbcseq` is already committed as `tests/fixtures/pbcseq.csv`). Committing a derived CSV fixture is therefore consistent with that precedent, not the `cunningham_lemke.py` download-on-demand pattern (which exists specifically because that source **states no licence** — a materially different situation). **Decision: commit `tests/fixtures/rossi.csv`**, exported once from R's `carData::Rossi` (canonical values), not the plain-text academic mirror (`utstat.toronto.edu`) used only to eyeball the shape in the prior research turn — the mirror's provenance/licence is unstated, same problem as Cunningham & Lemke, and `carData` gives an unambiguously-licensed source for the identical data.
   - **EBMT4**: source is `mstate` (CRAN, GPL >= 2), same licence class again. **Decision: commit `tests/fixtures/ebmt4.csv`**, exported once from R's `mstate::ebmt4`, following the `pbcseq.csv` precedent exactly (a small, well-known teaching dataset from a GPL package, redistributed as a flat CSV fixture, not regenerated at test/doc time).
   - Both exports are one-time, by hand, via `Rscript` against the scratch R lib already used for `mstate` this session (`rftvc-dev-workflow` memory's "scratch installs, lost on reboot" — the export itself is a throwaway script, not a maintained part of the repo, mirroring how `docs/bench/*.csv`/case-study `generated/*.csv` files are produced by hand and committed).

2. **Rossi reshape** (new `tests/fixtures/rossi.py`, mirroring `pbcseq.py`'s module shape: one loader function per shape needed).
   - Wide-to-long: for each subject, `emp1..emp52` are weekly employment indicators (`NA` from the week after `arrest`/censoring onward). Build one row per **run** of a constant `emp` value (not one row per week — a subject employed weeks 1-20 then unemployed 21-30 becomes 2 rows, not 30), `start`/`stop` in weeks, `event` on the last row only (`arrest`), covariate `employed` = that run's `emp` value, plus the static covariates (`fin`, `age`, `race`, `wexp`, `mar`, `paro`, `prio`, `educ`) copied onto every row. `week` (the subject's total observed weeks = `arrest`'s stop time, i.e. last non-`NA` `emp` index + 1, since `emp` is indexed from week 1 and `week` is right-censoring/event time) bounds the last interval.
   - `rossi_counting_process() -> pl.DataFrame` with columns `id, start, stop, event, employed, fin, age, race, wexp, mar, paro, prio, educ`.
   - A unit test (`tests/fixtures/test_rossi.py` or inline in `test_inspection_effects.py`'s sibling — placed in `tests/` proper since it is fixture-correctness, not a case study check) verifies: row count per subject = number of `emp` value changes + 1; the last row's `stop` equals that subject's `week`; `event` is 1 only on the last row and only for arrested subjects; a hand-checked subject (id=1, `emp` all-NA after week 20, i.e. never employed, `arrest=1`) gives exactly one row `(0, 20, event=1, employed=0)`.

3. **EBMT4 reshape** (new `tests/fixtures/ebmt4.py`).
   - **Outcome (competing risks).** Per patient: `event = 1` (relapse) if `rel.s == 1`; `event = 2` (death without relapse) if `rel.s == 0 and srv.s == 1`; `event = 0` (censored) otherwise. Time = `rel` when `event in {0, 1}` (relapse or censored at the relapse-free-survival clock — `rel` is defined as relapse time if it happened, else the same censoring time as `srv` when there was no relapse... **checked against `mstate`'s own vignette convention**: `rel`/`rel.s` already is relapse-or-censoring time with censoring at whichever of {relapse, death, admin censoring} came first, so `srv`/`srv.s` (which extends past a relapse to death) is only needed for the `event=2` branch's *time* — decision: `stop = rel` when `event in {0,1}`, `stop = srv` when `event == 2` (the patient relapse-censored at `rel` but the composite outcome needs the later death time). This mirrors `pbcseq_competing_risks`'s pattern of picking one terminal time/cause pair per subject.
   - **Time-varying covariate.** `gvhd`: 0 on `(0, ae]` (or the whole follow-up if `ae.s == 0`, i.e. no acute GvHD observed), 1 on `(ae, stop]` if `ae.s == 1` and `ae < stop` (a patient whose GvHD onset is at or after their terminal time contributes no "gvhd=1" interval — checked, not assumed, since `ae`/`rel`/`srv` are independently-censored marginal times in the raw data, not guaranteed ordered). Two rows per patient when the split applies (`(0, ae, gvhd=0)`, `(ae, stop, gvhd=1, event=terminal)`), one row otherwise — same construction shape as `pbcseq_counting_process`'s single-covariate-change interval split.
   - `ebmt4_competing_risks() -> pl.DataFrame` with columns `id, start, stop, event, gvhd, year, agecl, proph, match` (the four baseline factor covariates, one-hot or ordinal-encoded per the fitting script's own choice — CompetingRisksForestTV takes numeric `X`, so categorical encoding happens in the fitting script, not the fixture, matching how `btscs_war_duration.py` encodes `democ` etc. as already-numeric columns upstream rather than the fixture module doing it).
   - A unit test mirrors decision 2's: interval count per patient (1 or 2, by the `ae`-ordering rule above); `event` only nonzero on the last row; a hand-picked patient from `str(ebmt4)`'s printed `head()` (patient 2: `rel.s=1`, `rel=422` — event=1 at stop=422) checked exactly.

4. **Fits and comparison** (new `examples/rc_validation.py`, run by hand — not a docs case study yet, see Decision 6).
   - **Rossi:** `SurvivalForestTV` (same defaults as `btscs_war_duration.py`'s `forest()` helper: `n_estimators=500, min_ids_leaf=10, random_state=0`) vs `lifelines.CoxTimeVaryingFitter` on the same counting-process frame, exactly as `btscs_war_duration.py` already does side-by-side. `permutation_importance` (default `strata="time"`) and `hazard_effect` on `fin` and `age` (the two textbook Rossi effects: financial aid and age both reduce recidivism hazard) and on `prio` (prior convictions, increases it) and `employed` (the TVC itself — being employed should lower the hazard). `drop_column_importance` on the same set.
   - **EBMT4:** `CompetingRisksForestTV` vs a cause-specific Cox benchmark (two `lifelines.CoxTimeVaryingFitter` fits, one per cause, censoring the other cause — the standard cause-specific-hazard Cox approach, not a CIF regression, so it is comparable to what `CompetingRisksForestTV`'s per-cause hazards target). `permutation_importance(..., cause=1)` / `cause=2` for `gvhd` and the baseline covariates; `hazard_effect(..., cause=...)` for `gvhd`.
   - **No pass/fail rule** (unlike S16-S20's predeclared sims): there is no known ground-truth hazard on real data, so this section reports **directional plausibility against the published clinical/criminological literature**, not a numeric margin:
     - Rossi: `fin` and `age` importance/hazard-effect should be negative (protective); `prio` positive (harmful); `employed` negative. This is the well-replicated textbook result (Rossi, Berk & Lenihan 1980; every survival-analysis textbook's worked example agrees on direction, not magnitude).
     - EBMT4: acute GvHD (`gvhd=1`) is expected to show a **mixed** signature — historically associated with *higher* risk of treatment-related mortality (cause 2) but sometimes *lower* relapse risk (cause 1, the graft-versus-leukemia effect) in some disease subtypes; the case study reports both cause-specific numbers rather than asserting a single expected sign, since the true clinical literature itself is mixed (disease-subtype dependent) — the check here is "does the fit produce two directionally distinct cause-specific importances", not "matches a single textbook number".
   - A failed directional check (e.g. `fin` importance comes out positive) is a **stop-and-report** condition exactly like S20's failed sim rule: investigate before writing it up as a finding, since on real data a wrong-signed result is more likely a fixture bug than a genuine forest limitation, given how well-replicated these Rossi/EBMT effects are in the literature.

5. **What this validates, concretely** (the actual point of the exercise — a punch list, not prose):
   - Does `permutation_importance`/`hazard_effect`/`drop_column_importance` run end-to-end on real (not simulated) counting-process rows: real missingness patterns (Rossi's `NA` tail), real ties in event times, real covariate correlation structure (EBMT4's `agecl`/`year`/`proph` interactions) — anything S16-S20's clean synthetic generators wouldn't surface.
   - Does `CompetingRisksForestTV` + the S20 effects tools run on a real competing-risks dataset with a real time-varying covariate — the one combination no existing case study touches.
   - API friction: anything awkward, undocumented, or surprising while building the two fixtures and the fitting script gets written down verbatim in the "done" note (Decision 7) as raw input to the release-readiness pass — this plan does **not** fix API issues it finds; it reports them.
   - Runtime/memory sanity at realistic-but-modest real-world sizes (432 and ~2279 subjects) — not a formal timing benchmark like S17-S20's, just "did it run in a reasonable time on a laptop".

6. **Not a docs case study (yet).** Building a third `docs/source/case_studies/*.rst` page is out of scope for this plan — that is a documentation/release-pass decision (does the project want a criminology + a haematology case study alongside war-duration and PBC?), not a validation one. `examples/rc_validation.py`'s output is a plain report (Decision 7), committed under `docs/plans/` alongside this plan, not under `docs/source/case_studies/`. If the results are clean and interesting, promoting one or both to a real case study is an explicit follow-up recommendation in the done note, left for the user to decide.

7. **Findings report.** `docs/plans/rc-validation-findings.md` (new file): the two fits' numbers (importances, hazard-effect signs, Cox-vs-forest agreement), the directional-plausibility verdicts of Decision 4, and a bulleted "API friction / possible release-pass follow-ups" list. This is the plan's actual deliverable — everything else is infrastructure to produce it.
