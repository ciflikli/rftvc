# Research: Missing-Value Support

Answers to `docs/plans/missing-values-questions.md`. Facts only — no recommendation
between approaches (that's the design stage).

## Q1: How does randomForestSRC actually handle missing data?

`na.action` has (at least) two settings ([CRAN PDF](https://cran.r-project.org/web/packages/randomForestSRC/randomForestSRC.pdf), [rfsrc docs](https://www.rdocumentation.org/packages/randomForestSRC/versions/2.9.1/topics/rfsrc)):
- `na.action = "na.omit"` (default): drops any row with a missing value, then grows the forest on the complete cases.
- `na.action = "na.impute"`: **on-the-fly (adaptive tree) imputation**, not imputation as a preprocessing pass and not surrogate splitting. At each node, when a candidate split variable has missing values, those are filled by randomly drawing from the *non-missing in-bag values already present in that node* (i.e. a random hot-deck draw local to the current node), just enough to let every row be routed to a child. This can repeat/vary at multiple splits down the tree — it is "just-in-time," not a single global imputation.
- There is also a documented "cruder, faster" variant: no imputation at all — split search itself uses only non-missing rows for that variable, and rows with a missing value on the chosen split variable are then **randomly assigned** to a child after the fact.
- The package **explicitly does not use CART-style surrogate splitting**, and its own documentation/paper gives a reason: surrogate splits are expensive to compute per node and, because RF already randomizes which features are even considered at a node (`mtry`), a good surrogate correlated with the excluded split variable may not exist among the sampled candidates anyway. ([Tang & Ishwaran, "Random Forest Missing Data Algorithms," 2017](https://arxiv.org/pdf/1701.05305))
- No TVC/counting-process-specific missing-data mechanism was found in the search results; the counting-process (person-period) reformatting is described independently of missing-data handling, so nothing suggests `na.action` behaves differently for that data shape.

## Q2: What does the literature say about MIA vs. surrogate splits vs. imputation for trees?

- **MIA (Missing Incorporated in Attributes)**: at a candidate split, missing rows are **not** distributed by a rule fixed in advance — they are provisionally assigned as a block to *whichever* child (left or right) yields the better split-criterion score, and that choice is what gets stored for prediction-time routing. MIA makes no assumption about *why* data is missing (works under arbitrary/non-random missingness mechanisms). ([Tang & Ishwaran 2017](https://arxiv.org/pdf/1701.05305); "On the consistency of supervised learning with missing values," [Springer 2024](https://link.springer.com/article/10.1007/s00362-024-01550-4))
- **Surrogate splits**: as used in CART, doesn't scale well to forests for the reason above (expensive per-node search, undermined by random feature subsampling) — this is the same point randomForestSRC's own authors make for why they don't use it.
- **Head-to-head performance**: sources converge that MIA and surrogate splits are "the two best strategies" among tree-native approaches, with the better one depending on the covariate dependence structure; MIA specifically is reported to hold up well even under complex/non-ignorable missingness mechanisms. One comparison found multiple imputation gave the single best prediction accuracy overall, with surrogate splits close behind — but that comparison did not evaluate MIA in the same table (per the `arxiv.org/html/2110.09333` and `arxiv.org/pdf/2011.05433` results returned).
- No result specific to *survival* outcomes (vs. classification/regression) was found in this pass; the papers surveyed appear to be outcome-agnostic about the missing-data mechanism itself (MIA/surrogate/imputation are decided at the covariate level, independent of the response type).
- **Consistency theory**: the Springer 2024 paper's title ("On the consistency of supervised learning with missing values") indicates there is now a formal consistency argument for at least some of these approaches (MIA is discussed favorably), not just empirical comparison — full derivation not read in this pass, only the search snippet.

## Q3: Where would NaN have to be handled in rftvc's Rust engine, per approach?

Traced the actual code (not summarized from memory):

- **`Binned::fit`** (`rust/rftvc-core/src/data.rs:18-39`): sorts each column to compute bin edges via `col.sort_by(|a, b| a.partial_cmp(b).expect("NaN in X"))` (`data.rs:25`) — **this panics today if NaN reaches it**, this is the actual Rust-level enforcement point (independent of and behind the Python-level `check_array` rejection). `bin_of` itself (`data.rs:48-50`, `edges.partition_point(|&e| e < x)`) does not panic on NaN — for NaN `x`, no edge satisfies `e < NaN`, so it silently returns bin `0`. So the *only* current hard-stop on NaN is the sort in `Binned::fit`; if that were bypassed, NaN rows would silently bin as bin 0 today, not error.
- **`best_split_in`** (`rust/rftvc-core/src/splitter.rs:232-373`): grows the left child **one real bin at a time** (`for c in 0..nb - 1`, `splitter.rs:314`) using a single running difference array, comparing `used[c]` bins in increasing raw-value order. This loop structure assumes every bin has one well-defined position in that raw-value ordering. A reserved "missing" bin has no natural position in that order — MIA requires trying it in *both* children per threshold (not a single fixed position), which this single left-to-right sweep does not do as written. Implementing MIA here means either: (a) running the existing sweep twice per feature (once with missing rows pre-added to the left-base, once to the right-base) and taking whichever gives the better score per threshold, or (b) a structurally different loop. The unit-counting machinery (`min_hist`/`max_hist`, `ids_left`/`ids_right`, `splitter.rs:279-294`) is generic over *whatever* bin value is present, so it does not need a change per se — it would just need to correctly count a resampling unit whose rows include a missing value under whichever missing-direction is chosen for a given candidate.
- **`SplitCriterion` trait / `Profile`** (`rust/rftvc-core/src/criterion.rs:1-35`): scores an already-aggregated `Profile` (at-risk/event counts only) and has **no access to raw `X` at all** — it is agnostic to how rows were partitioned into left/right. Confirmed by reading the full `LtrcLogRank`/`Profile` code: nothing here needs to change for MIA specifically; whatever partition the splitter constructs, the criterion scores it identically. This significantly narrows the surface area: **missing-value handling is entirely a splitter-and-prediction-routing concern, not a criterion concern.**
- **`Tree::apply`** (`rust/rftvc-core/src/tree.rs:180-197`): routes with `x[*feature as usize] <= *threshold` — an IEEE-754 comparison. For a NaN `x[feature]` today this is always `false`, so a stray NaN would silently always route **right** — not documented, not intentional, just a byproduct of float comparison semantics. `Node::Split` (`tree.rs:9-19`) currently stores only `feature`, `threshold`, `left`, `right` — **no field exists for "which way do missing values from this split go."** Any native (MIA) approach needs a new per-split field (e.g. a bool or enum) persisted in `Node::Split`, threaded through `FlatForest`'s pickling format (`flat.rs`, `FORMAT_VERSION` is already versioned and has been bumped twice before for leaf-format changes — v1→v2→v3), and read by both `apply` and the prediction-time engine code (`predict_cumhaz`/`predict_paths`/etc. in `forest.rs`, not read in this pass but structurally parallel to `apply`).
- **Imputation-only approaches** (as an alternative to touching any of the above): would not need to touch `data.rs`/`splitter.rs`/`criterion.rs`/`tree.rs` at all — NaN would be resolved to a real number *before* it reaches the Rust engine, in Python, so the entire Rust engine is untouched.

## Q4: What can legitimately be missing in an rftvc row?

Checked every field's validation in `src/rftvc/_validation.py`:
- `start`/`stop`: `_start_stop` (`_validation.py:145-163`) explicitly requires `np.isfinite(start).all() and np.isfinite(stop).all()` (`_validation.py:158-159`), raising `ValueError` otherwise. **Not eligible for missingness** — makes sense, these define the row's position on the time axis.
- `event`: goes through `_as_bool`; not separately traced in this pass, but by construction (a row is either censored or has one of `1..=n_causes`) there is no meaningful "unknown outcome" state distinct from censoring in this framework.
- `measured_at` (optional, when given): `_validation.py:304-309` explicitly requires `np.isfinite(measured_at).all()`, with an explicit rationale in the error message: `"measured_at must be finite: an unknown measurement time cannot be checked"`. **Not eligible for missingness.**
- **`X` (covariates) is the only field with no explicit finiteness requirement of its own** — it is only rejected by the generic `check_array(X, dtype=np.float64, order="C")` calls in `_estimator.py:188` (fit) and `_estimator.py:405` (`_check_predict`, shared by every predict method), which reject NaN by sklearn's default (`force_all_finite`/no `allow_nan` passed).
- **Estimator tag**: `_BaseForestTV.__sklearn_tags__` (`_estimator.py:107-111`) sets `tags.input_tags.allow_nan = False` explicitly. This is sklearn's own formal declared contract (read by `check_estimator` and by meta-estimators deciding whether they may pass NaN through). Any missing-value support in `X` needs this tag flipped to `True`, which brings a new set of sklearn common tests into scope for `tests/test_sklearn_compat.py` (not enumerated in this pass, but this is the mechanism `check_estimator` uses to test NaN handling generically).
- Conclusion: **missing-value support in rftvc is structurally a covariate (`X`)-only feature.** `start`/`stop`/`event`/`measured_at` are all explicitly required complete by design, independent of which covariate-missingness approach is chosen.

## Q5: Does the existing `extrapolate="locf"` precedent map onto general missing-covariate handling?

No — traced `Extrapolate::Locf` through `rust/rftvc-core/src/forest.rs` (`grep` hits at lines 21, 208, 215, 298, 350, 554, 569, 594, 622, 690). It is a **prediction-time, along-a-path** mechanism only: when predicting beyond a subject's last observed `stop` (i.e. into the *future*, where no row exists at all yet), `Locf` says "hold the last row's covariates in force." It answers "what do we assume about time we have no data for," not "what do we do about a value that should exist at an observed time point but wasn't recorded." These are different problems: LOCF here never touches an already-present row's covariate vector, and it's a per-prediction-call option (`extrapolate=` parameter), not something that flows through model *fitting* at all. There is no existing code path that fills in a missing value *within* an observed row.

## Q6: What do the nearest competitors actually ship?

- **`scikit-survival` 0.28.0 (the version installed in this repo's `.venv`), verified empirically, not just from docs**: both `sksurv.tree.SurvivalTree` and `sksurv.ensemble.RandomSurvivalForest` **fit and predict successfully on `X` containing NaN**, including a fully-NaN column and ~10% scattered missingness, tested against `load_whas500()`. This is real, current, ensemble-level support — it inherits scikit-learn's own tree splitter's native missing-value handling (added in sklearn 1.3, which evaluates a candidate split with all-missing-left vs. all-missing-right and keeps whichever scores better — this **is** MIA in sklearn's own terminology, "missing goes to the child that improves the criterion"). `RandomSurvivalForest.__init__` does not even expose a `splitter` parameter (unlike `SurvivalTree`, which does) — meaning this behavior is not opt-in, it is simply how the ensemble is built.
- A web search on this specific question (`scikit-survival RandomSurvivalForest missing values NaN support`) returned an older/stale picture — a GitHub issue describing missing-value support as tree-only, not yet propagated to the forest level. **That is not the current state**: direct testing against the installed 0.28.0 (sklearn 1.9.1) shows full fit+predict NaN support at the forest level today. This is a real correction to trust the empirical test over the search result.
- No second Python survival-forest package was independently verified in this pass (time-boxed); `scikit-survival` is the only one checked directly, and it is also the closest existing comparator to rftvc in scope (sklearn-compatible survival forests).
- **Conclusion for this question specifically**: missing-value support is **not** a rare/skipped feature in this space anymore — the nearest direct Python competitor already has it, natively, at the ensemble level, via the same MIA mechanism the literature (Q2) treats as one of the two best tree-native approaches. Its absence in rftvc is a real, current gap against an existing comparator, not an unusually ambitious ask.

## Q7: Scoped engineering-cost estimate per approach

(Estimate only, informed by Q1-Q6; not a recommendation.)

- **Imputation-only** (fill `X` before it reaches the Rust engine, e.g. mean/median or per-subject LOCF): **Python-only**, no Rust changes, no `Node`/`FlatForest` format changes, no new sklearn tag semantics needed at the engine level (the forest never actually sees a NaN). Smallest surface area of the three. New test burden: correctness of whatever imputation rule is chosen (deterministic, so testable without a new closed-form-DGP simulation) plus, if this repo's own statistical-validity discipline (`docs/plans/simulation-validation-findings.md`) is applied here, likely a bias-under-a-known-DGP check for how much imputation degrades a known-truth recovery relative to a complete-data fit — the kind of check rows 1-4 of that inventory already do for other estimator behaviors.
- **Native MIA in the Rust splitter**: touches `data.rs` (how a "missing" bin is represented — e.g. whether it's folded into the existing `u8` bin space or a separate flag alongside `Binned`), `splitter.rs` (`best_split_in`'s single-direction sweep needs to become two-directions-scored, per Q3), `tree.rs` (`Node::Split` needs a new field, `apply` needs a NaN branch), `forest.rs` (every other prediction path that walks a tree the way `apply` does), `flat.rs` (a new `FORMAT_VERSION` bump, following the v1→v2→v3 precedent already in that file), and the Python-side `_estimator.py` (`allow_nan` tag flip, both `check_array` call sites, `_BaseForestTV.__sklearn_tags__`). **Both Rust and Python**, the widest surface area of the three. Per Q3, the `SplitCriterion` trait itself does *not* need to change. New test burden: likely the largest — both a Rust-level correctness check (candidate scoring matches brute force with missing rows tried both directions, mirroring the existing `child_summaries_match_brute_force` test pattern already in `splitter.rs`) and a Python-level statistical check (does MIA recover a known DGP's structure at least as well as complete-case deletion, under a declared missingness mechanism) if this repo's validation discipline is applied.
- **Surrogate splits**: not separately scoped in depth here since Q1/Q2 both independently report this approach is poorly suited to random forests specifically (not just "more expensive" — structurally undermined by per-node random feature subsampling, which rftvc already does via `max_features`). Noting it exists as a third option for the design stage to explicitly rule in or out, not recommending against it here.
- **Per-subject LOCF as an rftvc-specific imputation variant** (distinct from generic mean/median imputation): would reuse the *concept* already in `Extrapolate::Locf` (Q5) but not the code — that code operates purely at prediction time along a supplied path; a fit-time, TVC-aware "fill this row's missing value from this same subject's most recent non-missing row" would be new Python-side logic (likely in `_validation.py` or a new small module), still **Python-only**, still no Rust changes, but domain-aware in a way generic mean/median imputation is not.

## Surprises / constraints worth flagging to the design stage

1. **The `SplitCriterion` trait is fully decoupled from raw `X`** (Q3) — this was not obvious going in and meaningfully shrinks the "native MIA" cost estimate: it is a splitter-and-routing problem only, not a three-file rewrite across the whole scoring pipeline.
2. **`Tree::apply`'s current NaN behavior is silently wrong, not absent** (Q3) — if a NaN ever reached `apply` today (it currently cannot, because `Binned::fit`'s sort panics first, and Python's `check_array` rejects it before that), it would silently always route right with no error. This is dormant, not currently reachable, but worth knowing: there is no existing "safe default" to fall back on if a native-support implementation has a gap somewhere in a later engine version.
3. **The web search for Q6 (scikit-survival) returned meaningfully stale information** that direct local testing contradicted — the search-reported state ("tree-level only, not ensemble-level") is not what the actually-installed version does. Worth designing around verified-locally facts over search-result summaries where the two might diverge, given this package moves fast.
4. **`start`/`stop`/`event`/`measured_at` are all structurally excluded from "missing value support" by explicit, already-existing validation** (Q4) — there is no ambiguity to resolve there; this feature is unambiguously about `X` only, which simplifies scope for the design stage.
5. **A `FlatForest` format bump is not a new kind of risk for this codebase** — `FORMAT_VERSION` has already gone from v1 to v3 across prior slices (leaf cumulative hazards, then competing-risks cause counts per `flat.rs`'s own doc comment), so a v4 for a new `Node::Split` field (native-MIA path only) would be following an established, already-tested pattern, not a novel one.
