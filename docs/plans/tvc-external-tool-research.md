# Research: TVC vs. an external tool on a known-truth DGP

## Q1: does `tests/sim.py`'s existing DGP give `CoxTimeVaryingFitter` a fair home turf?

No. `tests/sim.py`'s hazard is `0.15 * exp(0.8*z + 0.8*(z>1) + 0.4*x0)` — the `0.8*(z>1)` threshold
indicator is a genuine non-linearity in `z`, and `rows()` (confirmed by reading it) hands the fitted
model only raw `[x0, z_k]`, never the indicator itself. `CoxTimeVaryingFitter` assumes a *linear*
log-hazard in whatever covariates it's given, so it would be misspecified here — not the "correctly
specified, strong home-turf baseline" role `CoxPHFitter` played for Slice 2's static DGP. Reusing
this DGP unmodified would make the comparison "two different kinds of wrong," not a real parity
check. **Conclusion: build a new, simpler DGP**, mirroring Slice 2's own precedent and its recorded
reason (a plan-review correction rejected subsetting an existing TVC DGP as insufficient).

## Q2: `CoxTimeVaryingFitter`'s prediction API

Explored directly (`.venv`, cargo `PATH`) on synthetic counting-process data:

- `.fit(df, id_col=, start_col=, stop_col=, event_col=)` — same shape already used in
  `examples/rc_validation.py`.
- No `predict_survival_function` for the time-varying case (unlike `CoxPHFitter`). Available:
  `predict_partial_hazard(df)` (returns `exp(beta @ x)` per row) and
  `baseline_cumulative_hazard_` — a `DataFrame` indexed by stop-time, giving the **non-parametric
  (Breslow-type) baseline cumulative hazard** up to that time, as a step function (confirmed: for
  unit-interval data, this lands exactly on integers 1, 2, 3, ...).
- To reconstruct `S(t | known covariate path)`: for each unit interval `(k, k+1]` with covariate
  value `z_k`, take the baseline cumulative-hazard **increment** over that interval
  (`baseline_cumulative_hazard_` at `k+1` minus at `k`) times `predict_partial_hazard` at `z_k`,
  and cumulative-sum across intervals up to `t` — exactly the same piecewise-constant-hazard
  convention this codebase already uses everywhere else (e.g. `bench/pe_score_convergence_sim.py`'s
  own `true_cumhaz`, the oracle stubs in `bench/tvc_perm_sim.py`/`bench/tvc_landmark_sim.py`). No
  API footgun found — this is a standard, well-documented use of the Breslow baseline.

## Q3: the new DGP

Simplest genuinely log-linear external-TVC hazard, correctly specified for `CoxTimeVaryingFitter`:
drop `tests/sim.py`'s threshold indicator and its `x0` (Slice 2 also went to a single covariate for
its static case): `hazard = rate0 * exp(beta * z_k)`, `z_k ~ N(0,1)` redrawn per unit interval
`(k, k+1]`, `k = 0..7`. Same censoring convention as `tests/sim.py`/Slice 2
(`C ~ Uniform(2, 8)`, admin end at 8, eval horizon 6, 61-point trapezoid grid) — reusing established
conventions rather than inventing new ones for this slice specifically.

Closed form: within-interval hazard is constant, so `Λ(t | path) = rate0 * Σ_{j<k} exp(beta*z_j) +
rate0 * exp(beta*z_k) * (t - k)` for `t` in `(k, k+1]` — same shape as
`bench/pe_score_convergence_sim.py::true_cumhaz`, verified against numerical integration below.

## Q4: does a real ISE gap emerge, calibrated out-of-band?

Built a prototype script (later promoted to `bench/tvc_coxtv_truth_check.py`) with `rate0=0.15,
beta=0.8` (matching `tests/sim.py`'s scale), `n_train=400, n_test=200, n_estimators=200`. First
attempt hit a real bug: naively `reindex`-ing `CoxTimeVaryingFitter.baseline_cumulative_hazard_` to
exact integers 1..8 gave `NaN` (event times in this DGP are continuous, not aligned to interval
boundaries except for non-terminal rows) — fixed with a proper step-function lookup
(`np.searchsorted` on the baseline's own index) instead of assuming exact-integer alignment. Never
trust an unverified helper's output — this would have silently produced `NaN` epsilon comparisons
that trivially "pass" (`NaN <= x` is always `False` in numpy but `nan_to_num` tricks or a loose
`<=` could mask it) had the pilot's own printed values not been inspected directly.

Pilot run, out-of-band seeds 10000-10004:

| seed | rftvc ISE | cox ISE |
|---|---|---|
| 10000 | 0.0936 | 0.0034 |
| 10001 | 0.1029 | 0.0080 |
| 10002 | 0.1015 | 0.0033 |
| 10003 | 0.1001 | 0.0073 |
| 10004 | 0.0850 | 0.0033 |

Mean rftvc ISE ≈ 0.0966, mean cox ISE ≈ 0.0051, mean gap ≈ 0.0915. A second out-of-band batch
(20010-20014): mean rftvc ISE ≈ 0.0934, mean cox ISE ≈ 0.0073, gap ≈ 0.0861. The gate's own seeds
(0-9, R=10): mean rftvc ISE ≈ 0.0957, mean cox ISE ≈ 0.0041, gap ≈ 0.0916. All three batches agree
closely (gap 0.086-0.092) — the effect is real and stable, same qualitative shape as Slice 2's
static result (rftvc pays a statistical-efficiency cost against a correctly-specified Cox model on
data generated by exactly that model's assumptions), though the absolute ISE and gap are both
larger here than Slice 2's static case (0.041/0.0038 there vs. ~0.095/0.005 here) — expected, since
per-interval TVC estimation is a harder problem than a single static covariate. Following Slice 2's
exact convention: an additive epsilon roughly double the observed gap, **`EPSILON = 0.18`**.

## Q5: runtime

`CoxTimeVaryingFitter.fit` on ~400 subjects x up to 8 rows each took well under 0.1s per
replication — negligible next to `SurvivalForestTV`'s fit time. R=10 at `n_estimators=200`: ~4.2s
measured directly, in the same range as Slice 2's own `slow`-tier gate (~2s) and well within what
Slices 5-10 established as viable for the default tier. No reason this needs to be `slow`.
