# 0.4.0 roadmap: a credible Python reference for survival forests

Status: proposal, 2026-09-30. This is a release plan, not a claim that the
features or benchmark results below already ship.

## Positioning

Lead with the package's distinctive capability: subject-aware forests for
changing covariates, delayed entry, and competing events, with native Python
prediction and evaluation. Make static right-censored survival competitive too,
but do not optimize solely for a static fit-time leaderboard. A premier offering
must be statistically dependable, fast for *useful predictions*, and easy to
inspect and publish.

Already present in 0.3.0: Rust/Rayon fitting, scikit-learn estimators, static and
counting-process rows, competing-risk CIFs, landmark models, NaN routing,
categorical encoding, OOB predictions, inspection, evaluation, and six plotting
helpers. The existing benchmarks are useful baselines, not release claims:
`docs/bench/fit-matrix.md` uses one timed fit per cell and version 0.2.0;
`docs/bench/parity-suite.md` shows static accuracy equivalence on five of six
datasets under its prespecified margins; `docs/bench/s14-cr.md` compares
competing-risk CIFs with randomForestSRC on PBC.

## P0: benchmark and statistical trust (release blocking)

1. **Publish a reproducible forest benchmark suite.** Extend `bench/fit_matrix.py`
   into a version-pinned, fresh-process runner with at least five measured
   repetitions after warm-up, fixed CPU/thread limits, machine details, raw
   JSONL, and a report generator. Record median and spread of fit time,
   prediction time, and incremental model memory separately from whole-process
   peak RSS. Compare `rftvc` with scikit-survival RSF for static survival,
   `comprisk` for static competing risks, and `ranger`/`randomForestSRC` for
   cross-language context. Include both scikit-survival's `low_memory=True`
   mortality path and curve-capable mode; compare the same output quantity at
   the same prediction grid. Label unsupported tasks, rather than treating them
   as losses. Publish versions, configuration, data generator, and exact command.
2. **Pair speed with prediction quality.** Use identical subject splits and
   evaluation horizons. Report Harrell/Uno concordance as appropriate,
   time-dependent AUC, IPCW integrated Brier, calibration, and competing-risk
   cause-specific Brier/CIF error. Use paired bootstrap intervals or repeated
   folds. Include censoring rates, event counts, and a no-skill baseline. Test
   static, rare-event, wide, tied-time, missing, categorical, two-cause, and
   truly time-varying scenarios. The current TVC timing generator perturbs a
   covariate *after* generating event times from baseline covariates; replace it
   with a known-truth path-dependent hazard generator for quality comparisons.
   Keep real-data folds for external validity and simulations for mechanism
   checks. Benchmark `rftvc`'s TVC and competing-risk features on their own
   merits when another package lacks an equivalent interface.
3. **Make correctness gates explicit.** Check step-function monotonicity,
   `sum_k CIF_k(t) <= 1`, invariance to row order and thread count, subject-safe
   resampling, no future covariates at a landmark, and agreement with
   independently calculated small-case oracles. Keep the existing simulation
   truth and R parity suites in the release evidence. Define a visible accuracy
   non-regression rule before optimizing internals: on the paired static suite,
   no material deterioration beyond the existing C ±0.02 and IBS ±0.01 margins;
   on TVC/CR truth suites, no deterioration beyond scenario-specific Monte Carlo
   uncertainty. Investigate the high-dimensional breast-cancer parity miss.

## P1: performance users will feel

4. **Profile prediction before changing algorithms.** The existing matrix shows
   `rftvc.predict()` slower than scikit-survival's reduced-memory mortality
   path on some static cases, despite much faster fitting. Add direct Rust
   mortality accumulation, batched horizon prediction, and sparse/event-grid
   traversal only if profiling identifies the cost. Keep curve predictions
   numerically unchanged. Measure latency at 1, 100, and 10,000 subjects,
   across 1/4/all threads, as well as fit time and memory. Target at least a
   2x median improvement on the current static `predict()` bottleneck with no
   material quality change; report cases that do not improve.
5. **Expose a deliberate speed/precision choice.** Benchmark exact event-time
   grid against `ntime` coarsening over event-rate, censoring, and cause-count
   sweeps. Show error and memory as functions of grid size. Offer a documented
   recommendation or `auto` policy only after demonstrating bounded error;
   preserve the existing warning when coarsening drops rows/events.
6. **Investigate categorical width.** Current one-hot encoding is simple and
   interoperable, but can inflate split search and importance cost. Profile
   high-cardinality features and compare native categorical partitioning or a
   validated grouped split candidate against the current approach. Ship a new
   strategy only if it improves held-out quality or fit/resource cost without
   leakage or unstable unseen-level behavior.

## P1: publication-grade graphics and inspection

7. **Add an interactive patient-path view.** A linked Altair view should show
   observed covariates and landmarks, predicted survival/CIF over time, and
   absolute risk at selected horizons. Make the observed/forecast boundary
   unmistakable. A cause-specific stacked CIF view should display residual
   event-free probability and maintain the sum-to-one constraint. Keep the
   numerical data available as a table for inspection and independent plotting.
8. **Add diagnostics that inform decisions.** Plot Brier and calibration *over
   time*, grouped risk calibration with counts/at-risk numbers, and side-by-side
   model comparisons with bootstrap uncertainty where the metric supports it.
   Add compact feature-effect and importance views using the existing
   inspection outputs. Support SVG/PNG/HTML export, accessible palettes,
   readable labels, and bounded chart payloads for large cohorts. Plot helpers
   should consume computed results; statistical estimation stays in metrics or
   inspection. Visual tests should check labels, dimensions, and key chart data.
9. **Consider minimal depth, with its limits.** `export_tree()` makes a fast
   split-depth summary feasible. Group one-hot columns back to source features.
   Document that correlated and high-dimensional features can distort rankings;
   validate against known-signal simulations before advertising variable
   selection. This is a useful complement to the existing permutation and
   drop-column importance, not a replacement.

## P2: conditional candidates, not release blockers

- **Warm start / incremental trees:** useful for tuning, but requires identical
  RNG streams, fitted-design validation, and OOB update semantics. Benchmark
  before adding API surface.
- **GPU / SHAP / oblique splits:** each can be valuable, but each brings a
  substantial correctness and maintenance burden. Prototype only against a
  defined quality or latency bottleneck; do not promise these for 0.4.0.

## Suggested release sequence

| Milestone | Deliverable | Exit evidence |
|---|---|---|
| A | Benchmark protocol and quality suite | Reproducible raw runs, pinned versions, paired quality report, transparent unsupported cases |
| B | Prediction hot-path optimization | Profile before/after, exact output parity, multithread determinism, memory/latency table |
| C | Path and diagnostics graphics | Complete worked case study, exports, accessibility and large-data checks |
| D | Release candidate | Existing test/CI/wheel gates, benchmark rerun on RC wheel, docs and changelog consistent with measured results |

The feature freeze should follow A: data may reveal a different bottleneck or
quality weakness. Publish measured tradeoffs rather than a universal "fastest"
claim. If B or C is not validated in time, defer the unfinished item rather
than dilute A's evidence.
