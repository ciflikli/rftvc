## Decisions (defaults; revisit in review)

1. **Module placement.** `inspection.py` gains `hazard_effect`/`path_effect` as two more public functions (added to `__all__`), following S17–S19's pattern of keeping public dispatch in `inspection.py` and moving nontrivial per-family logic into `_inspection/` submodules. A new `_inspection/_effects.py` holds the actual grid/window computation (`_hazard_grid`, `_split_at`, the `path_effect` core), mirroring `_score.py`'s role for `permutation_importance`. **Correction (Review log finding 4):** `_inspection/__init__.py` currently holds only a module docstring (`"""Private helpers of \`\`rftvc.inspection\`\`."""`) and does **not** re-export `_loco, _score, _strata, _units` — `inspection.py` imports them directly (`from ._inspection import _loco, _score, _strata, _units`, which works because they are submodules of the `_inspection` package, not because `__init__.py` re-exports names). `_effects` needs no `__init__.py` change at all: `inspection.py` simply adds `_effects` to its existing `from ._inspection import ...` line, exactly as the other four submodules are already imported.

2. **`hazard_effect` signature** (design §4.1, unchanged from the design):
   ```python
   hazard_effect(estimator, X, y, *, feature, values=None, windows=8, kind="average", ids=None, cause=None) -> Bunch
   ```
   - `estimator`: any fitted `SurvivalForestTV`/`CompetingRisksForestTV`/`LandmarkSurvivalForest`/`LandmarkCompetingRisksForest` (`_family(estimator, fn="hazard_effect")`, unmodified). For a landmark estimator, `X` is the raw long frame and `y`/`ids` must be `None` (as `permutation_importance`'s landmark branch), dispatched to `_pe_landmark`-style stacked rows via `model._landmark_data(df)`; `windows` are on the horizon clock as S17–S19 established, and `ids` in the signature refers to counting-process rows only (landmark ids come from the frame).
   - `feature`: one name or index (not a unit — `hazard_effect` targets a single covariate's marginal effect, so it reuses `_units._column`, not `resolve_units`/`resolve_landmark_units`).
   - `values=None`: 20 quantiles of `X[:, feature]` (`np.quantile(Xe[:, j], np.linspace(0, 1, 20))`, deduplicated — ties can give fewer than 20).
   - **Computation** (`_inspection/_effects.py._hazard_grid`), per window `m` in a loop (not a dense `(n, M)` array — `tvc-plan.md` Q1 requires the metric family to stay `O(n)` per window, not `O(n×M)`; `piecewise_exponential_score`'s own loop (`metrics.py:756-761`) already computes the exposure `e = clip(min(stop, hi) - max(start, lo), 0, None)` one window at a time for exactly this reason, so `hazard_effect` reuses that same **one-window** computation via a new `metrics._window_exposure_1(start, stop, lo, hi) -> (n,)` helper — a 1-D-per-call factoring of the existing inline expression, not the `(n, M)` vectorization considered and rejected in an earlier draft of this decision as a memory regression): `e_rm = _window_exposure_1(start, stop, w[m], w[m+1])`. For each grid value `v` and window `m`: `Xr = Xe.copy(); Xr[:, feature] = v`; `H = predict(Xr, np.arange(Xr.shape[0]))` (the **two-argument** `predict(Xr, rows)` callable `_heldout`/`_pe_landmark` already build — `_heldout`'s closure calls the native `forest.predict_cumhaz`/`predict_cause_cumhaz` directly, not a public estimator method, and always takes `rows` even when unused by the fixed-profile case; `hazard_effect` calls `_heldout` unconditionally for counting-process estimators, exactly as first drafted, but must call its `predict` with the same two-argument signature every other caller in `inspection.py` uses, not the one-argument `predict(Xr)` an earlier draft of this decision wrote by mistake); `rate_m = (H[:, m+1] - H[:, m]) / (w[m+1] - w[m])`; the window's value is `sum(e_rm * rate_m) / sum(e_rm)` over rows with `e_rm > 0` (rows with zero exposure in `W_m` contribute nothing — this is the "at risk in `W_m`" restriction the design's estimand names, achieved by the exposure weight itself rather than a separate risk-set mask). **A window with `sum(e_rm) == 0` across every row** (possible on held-out data even though `windows` is training-derived) gives `hazard[v, m] = NaN` for every `v` (not 0, not an error — there is nothing to average), and `support_mask[:, m] = False` for every `v` (no rows are at risk, so no value is "in support"); `kind="individual"`'s per-row rate is already `NaN` there since no row has `e_rm > 0`. Tested explicitly (Tests, below).
   - **`support_mask (n_values, M)`:** `v` is inside `[P5, P95]` of `x_j` among rows with `e_rm > 0` in `W_m` (computed once per window from the *un-replaced* `Xe[:, feature]`, weighted by `e_rm` via `np.quantile`'s unweighted quantile on the boolean-masked subset — the design does not ask for exposure-weighted percentile boundaries, only "the rows at risk", so an unweighted quantile over the at-risk row subset is the direct reading).
   - **CR:** `H` has shape `(n, J, M+1)`; `cause=None` returns `(n_values, J, M)`, `cause=k` returns `(n_values, M)` (selecting one cause axis before the window loop, mirroring `_pe_codes`'s `cause` handling).
   - **`kind="individual"`:** returns `(n_rows, n_values, M)` per-row rates (`rate_m` above, before the exposure-weighted average), masked to `NaN` where `e_rm == 0` (a row not at risk in that window has no rate to report — `NaN`, not 0, since 0 would misrepresent "not evaluated" as "zero hazard"); `kind="average"`'s `values`/`support_mask`/`window_edges` are the exposure-weighted collapse of the same per-row array, so the design's "individual averages (exposure-weighted) to average" test is a direct consequence of computing both from one `rate_m` array, not two independent code paths.
   - **Errors:** `feature` naming the ids column (counting-process) or `"landmark"` (landmark) raises via the reused `_column`/`resolve_landmark_units`-style check; `kind` outside `{"average", "individual"}` raises; landmark `cause=None` with a survival (non-competing) landmark model is fine (no `cause` applies, same as `_pe_landmark`'s `competing` guard).

3. **`path_effect` signature** (design §4.2):
   ```python
   path_effect(estimator, X, intervals, ids, *, feature, delta, from_time, horizons, origin=None, cause=None, extrapolate="none") -> Bunch
   ```
   - **Landmark estimators raise `TypeError`** immediately in `_family`'s caller (a new explicit check at the top of `path_effect`, not a `_family` flag — `_family`'s existing `(is_landmark, competing)` tuple is reused only to detect this case; landmark models have no "path" concept per design's own wording, so this is a hard `TypeError`, not a `ValueError`, matching Python's convention for "this operation is not defined for this type" rather than "bad argument value").
   - **Clock and validation** (design's explicit ask, Codex review finding 5, refined by a second review pass — see Review log finding 2): `X`/`ids` must first go through `estimator._check_predict(X, None, ids)` (the same DataFrame-to-array conversion and ids-column-name resolution `predict_cumulative_hazard` itself runs at `_estimator.py:638` before ever calling `_path_args`) — `path_effect` cannot call `_path_args` directly on a raw, unchecked `X`/`ids` the way an earlier draft of this decision assumed. After that, `estimator._path_args(X, intervals, ids, origin, extrapolate)` gives `(X, start, stop, offsets, origin)` ordered by `(subject, start)`, with `origin` already resolved and range-checked (`first_start <= origin <= last_stop`) — but `_path_args` returns **no subject id labels** (`offsets` delimits subjects positionally, unlabelled), so `path_effect` separately computes `id_labels = np.unique(ids, return_index=True)` sorted by first appearance (the same convention `piecewise_exponential_score`'s `by_id` and S17's `id_labels` use) to have a name for each `offsets`-delimited subject before validating and reporting. `path_effect` adds its own checks on top: every `horizons` value `h` must satisfy `origin_i <= from_time <= h <= last_stop_i` per subject `i`, unless `extrapolate="locf"` permits `h > last_stop_i`; `from_time < origin_i` for any subject raises `ValueError` naming the offending subject ids from `id_labels` (design §4.2's explicit "names the subjects" requirement — a plain index would not satisfy it).
   - **Row splitting at `from_time`** (design's explicit requirement, "rows straddling `from_time` are split there, covariates copied"): a new `_inspection/_effects._split_at(X, start, stop, offsets, from_time)` that, for each subject's rows (delimited by `offsets`), finds the row with `start < from_time < stop` (if any — `from_time` exactly on a boundary needs no split) and replaces it with two rows `(start, from_time)` and `(from_time, stop)`, both carrying the same covariate values as the original row (the shift is applied only to the second copy, in the next step). Subjects where `from_time` is outside every row's `(start, stop]` (i.e., `from_time` is at the very start or after the last stop) are handled by the existing `origin <= from_time <= last_stop` validation, which already excludes the "no such row" case except at exact boundaries (`from_time == start` of the first post-origin row needs no split either).
   - **The shifted path:** every row (post-split) with `start >= from_time` gets `x_j` replaced by `delta(x_j, start)` if `delta` is callable, else `x_j + delta`. Rows with `start < from_time` are unchanged. This gives two full interval sets — the original and the shifted — both passed through `predict_cumulative_hazard(..., intervals=..., ids=..., origin=..., extrapolate=...)` (survival) or `predict_cumulative_incidence`/`predict_cumulative_hazard(cause=...)` (CR), at `times=horizons`.
   - **Extrapolation beyond `last_stop`:** `extrapolate="locf"` is passed straight through to the underlying `predict_*` call (which already implements LOCF via `_path_args`'s own `extrapolate` handling) for **both** the original and shifted path — `path_effect` does not need its own LOCF logic, only to plumb the keyword through, since the two predict calls already agree on how to extend a path past its last observed row.
   - **Output:** `per_subject = shifted − original`, shape `(n_subjects, n_horizons)` (survival: `Δ F = ΔS_shifted - ΔS_original`... concretely `original_risk = 1 - predict_survival_function(...)`, `shifted_risk = 1 - predict_survival_function(shifted...)`, `per_subject = shifted_risk - original_risk`; CR: `predict_cumulative_incidence` directly, since CIF is already the risk scale, `per_subject = F_shifted - F_original`); `mean = per_subject.mean(axis=0)`; `horizons` echoed back as given (validated, not resolved from data — unlike `hazard_effect`'s `windows`, `path_effect`'s `horizons` has no "default from the estimator" case in the design).
   - **CR shape:** `cause=None` gives `(n_subjects, J, n_horizons)` (matching `predict_cumulative_incidence`'s own `causes_`-order shape), `cause=k` gives `(n_subjects, n_horizons)`.
   - **`delta=0` (or a callable returning `values` unchanged) gives exactly 0`,** a design-stated test: since the shifted path then equals the original path bit-for-bit before prediction, this holds by construction — no special-cased "delta is zero" branch is needed, just the same two `predict_*` calls scored on identical inputs (documented as a property, not implemented as a shortcut, so the code path being tested is the real one).
   - **Docstring wording (design's explicit requirement, verbatim per the Executive summary):** "Prediction along a specified covariate path. Valid when `x_j` is external (D4). Not a causal effect unless `x_j`'s effect on the hazard is unconfounded given the other covariates." with a reference to Keogh & van Geloven 2024.

4. **`metrics._window_exposure_1` extraction (corrected — Review log finding 1).** `piecewise_exponential_score`'s per-window loop (`metrics.py:756-761`) computes `e = clip(min(stop, hi) - max(start, lo), 0, None)` **one window `m` at a time**, inside a `for m in range(M)` loop, specifically to keep peak memory at `O(n)` rather than `O(n×M)` — `tvc-plan.md`'s own Q1 plan-level decision states this explicitly ("Cells are computed one window at a time... this matters at scale: a dense float64 `(n, M)` array is 512 MB at 1M rows and M = 64"). An earlier draft of this decision proposed vectorizing `e` into a dense `(n, M)` array shared by both call sites — **rejected**: that is exactly the memory regression Q1 warns against, not a "pure refactor". The corrected extraction is a **single-window** helper, `metrics._window_exposure_1(start, stop, lo, hi) -> ndarray (n,)` (`e = clip(minimum(stop, hi) - maximum(start, lo), 0.0, None)`), called once per `m` inside `piecewise_exponential_score`'s existing loop (replacing its inline `e = ...` line with `e = _window_exposure_1(start, stop, lo, hi)` — same arithmetic, same one-window-at-a-time memory shape, still a behaviour-preserving refactor) and once per `m` inside `hazard_effect`'s own per-window loop (decision 2). This is the one piece of existing code S20 touches outside `inspection.py`/`_inspection/`.

## Tests (`tests/test_inspection_effects.py`)

## Simulations (T9; rule from design §7.5, predeclared)
Reuses the R = 50 / 10-rep-pilot convention and `_stubbed`/`_carrier`/`holm_reject`/`mc_se` helpers of `bench/tvc_perm_sim.py`, and `tests/sim.py`'s S3 generator (`hazard(x0, z)`, `simulate`, `rows`, `true_survival`) for the known external-covariate hazard. **Fully predeclared per Review log finding 8** (an earlier draft left `delta`/`from_time`/`horizons`/the test-path construction unspecified, which the S17–S19 convention of predeclaring every sim parameter does not allow):
- **Test paths, not `simulate`'s observed (possibly censored/terminated) rows.** S3's `rows()` helper stops each subject's path at its own event or censoring time, so most subjects have no observed rows at `from_time` or beyond — `path_effect` needs a *complete* external-covariate path through every `horizon`, exactly as `tests/sim.py`'s own `replicate()` (line 84-91) already builds for its prediction-accuracy check: fresh test subjects `tx0, tz = rng.normal(size=n_test), rng.normal(size=(n_test, K))` with a full `K`-interval path (`Xp`/`starts`/`iv` built the same way `replicate` builds them), not run through the event/censoring simulator at all — the oracle-vs-model contrast needs the covariate path defined at every horizon, which only a *fully specified* (uncensored, unterminated) path guarantees.
- **Fixed parameters:** `feature="z"` (column 1 of the 2-column `[x0, z_k]` row layout `rows()` produces); `delta=1.0` (a full-SD shift of the standard-normal `z`, large enough to give a non-negligible `Δ` given the generator's `0.8` coefficient on `z`, small enough to stay inside `z`'s typical simulated range); `from_time=3.0` (mid-follow-up, `K=8`/`HORIZON=6.0`, an interval boundary so no row needs mid-interval splitting in the base case — the *separate* straddling-row unit test, above, covers the mid-interval case on a hand-built fixture); `horizons=[4.0, 5.0, 6.0]` (all `>= from_time`, inside `[0, HORIZON]`, so every horizon has a well-defined, non-trivially-zero true `Δ` — `from_time` itself is excluded from `horizons` since `Δ(from_time) = 0` by construction and is not an informative pass/fail point).
- **Oracle `Δ risk`:** for each test subject, `hazard(x0, z)` gives the true piecewise hazard on the *original* path; a second call `hazard(x0, z_shifted)` with `z_shifted[:, k] = z[:, k] + delta` for every interval `k` with `k >= from_time` (i.e. `k >= 3`, matching `path_effect`'s "shift from `from_time` onward" semantics on this generator's unit-interval grid) gives the hazard on the *shifted* path; both are integrated to `t = horizon` (reusing `true_survival`'s cumulative-hazard construction, called on `(x0, z)` and `(x0, z_shifted)` separately) to give `true_risk_original[horizon]` and `true_risk_shifted[horizon]`; `true_Δ[horizon] = true_risk_shifted - true_risk_original`, averaged over the test sample.
- **Model side:** fit `SurvivalForestTV` on S3 training rows (`simulate`/`rows`, as `tests/sim.py.replicate` already does); call `path_effect(tvc, Xp, iv, ids, feature=1, delta=1.0, from_time=3.0, horizons=[4.0, 5.0, 6.0])` on the fresh full-path test subjects; `path_effect`'s `mean` is the model-side estimate of `Δ risk` at each horizon.
- **Pass:** `|mean bias|` (mean over `R=50` replications of `path_effect`'s `mean` minus `true_Δ`) `≤ 0.1 * |true_Δ|` at each of the three horizons.
- **Fast smoke test** (per `tvc-plan.md`'s simulation convention, §7.8/S17-S19's own `test_..._sim_truth.py` fast/slow split — an earlier draft of this plan omitted this): `tests/test_tvc_sim_truth.py` gains a `path_effect` fast case (`R=1`, small `n_train`/`n_test`, asserting only that the machinery runs end-to-end and returns finite, correctly-shaped output — no statistical pass rule) and a slow case (`R≈10`, the same §7.5 pass rule at reduced power, `pytest.mark.slow`), alongside `bench/tvc_path_effect_sim.py`'s own `R=50` full run (which writes `docs/bench/s20-effects/path_effect.csv`, following S17-S19's `docs/bench/sNN-*/` naming).
- The 10-rep pilot (`python -m bench.tvc_path_effect_sim pilot`) checks the Monte Carlo SE of the bias against 1/7 of this margin, as S17–S19's own pilots do.
- A failed rule blocks the merge unless the user accepts a documented deviation.

**T9 result (2026-09-27): FAILS AS DECLARED, at both the R=10 pilot and the full R=50 run — awaiting a user decision.** `docs/bench/s20-effects/path_effect.csv` (`n_train=1000, n_test=1000, n_estimators=200`, matching S17-S19's own sim scale, corrected from an initial `n_train=400` draft that arbitrarily matched `tests/sim.py`'s toy default instead):

| horizon | true_Δ (oracle, n=100,000) | mean bias (R=50) | MC-SE | margin (0.1·\|true_Δ\|) | margin/7 | pass |
|---|---|---|---|---|---|---|
| 4.0 | 0.1089 | −0.0272 | 0.0015 | 0.0109 | 0.0016 | **no** |
| 5.0 | 0.1459 | −0.0326 | 0.0017 | 0.0146 | 0.0021 | **no** |
| 6.0 | 0.1497 | −0.0300 | 0.0017 | 0.0150 | 0.0021 | **no** |

The MC-SE is well under margin/7 at every horizon (the pilot's own power-projection rule is satisfied), so this is a clean, well-powered failure, not an underpowered test that might pass with more replications. The forest's `path_effect` estimate is systematically ~2.0-2.5× the allowed margin *below* the true Δ risk at every horizon and every replication (`path_effect.csv`'s 50 rows are uniformly below `true_Δ`, not a mix) — a real, reproducible effect, not sampling noise landing on the boundary.

**Not a code defect, verified directly:** `inspection.path_effect` and this script's own `true_delta` formula were checked against each other using an exact-hazard stub in place of the fitted forest's `forest_` (mirroring `tests/test_inspection_effects.py`'s `PathOracle`/`_stubbed` pattern) — with the true S3 hazard standing in for the model, `path_effect`'s output matches `true_delta` to full float precision on the same sample (`0.11032646 0.14639413 0.15027394` both sides). The discrepancy is entirely in the *fitted forest's* estimate of the path effect at this sample size, not in the estimand computation.

**Mechanism, confirmed by direct investigation (2026-09-27), superseding the initial "windows compounding" hypothesis above.** `path_effect`'s bias decomposes exactly as `bias_shifted(h) − bias_unshifted(h)`, where `bias_original(h)`/`bias_shifted(h)` are the *base* estimator's own bias (`predict_survival_function(..., intervals=...)`, no delta contrast at all) on the unshifted and shifted paths respectively, against the same oracle `true_delta` truth. Computed directly on the fitted forest (n_train=1000, seed=0; a fresh n=5000 test sample; no stub):

| horizon | bias, unshifted path | bias, shifted path | difference (= `path_effect`'s own bias) |
|---|---|---|---|
| 3.5 (0.5 units past `from_time`) | −0.0109 | −0.0099 | **+0.0009** (≈0) |
| 4.0 | −0.0166 | −0.0335 | −0.0170 |
| 5.0 | −0.0284 | −0.0502 | −0.0217 |
| 6.0 | −0.0446 | −0.0584 | −0.0139 |

Two stacked, both-real mechanisms, neither a `path_effect` code defect (the estimand computation itself was already verified exact against an oracle stub):
1. **The base estimator's cumulative-risk-along-a-path prediction is itself increasingly biased downward as the integration horizon grows**, present even on the *unshifted* path with no delta contrast involved (−0.011 at h=3.5 growing monotonically to −0.045 at h=6.0). This is a genuine, previously undocumented property of `SurvivalForestTV`'s path-based prediction — not a re-confirmation of anything already written in `tvc-research.md`, `tvc-design.md` or `tvc-deviance.md` (checked; the closest existing note, "composition drift" in `tvc-research.md` §1.1, is about leaf hazard *shape* reflecting population mix, not this).
2. **The forest under-predicts hazard more severely in the higher-hazard region the shift creates**: at every horizon, `bias_shifted` is more negative than `bias_unshifted` — classic ensemble-averaging shrinkage toward the bulk of the training distribution, worse at the elevated hazard level a full-SD covariate shift produces. This is the part that does **not cancel** in `path_effect`'s subtraction and is what actually produces its reported bias.

**The single-window isolation is the decisive evidence.** At h=3.5 (half an interval past `from_time`), mechanism 1 is already substantial and nearly identical on both paths (−0.011 vs −0.010), so it cancels almost perfectly in the difference: `path_effect`'s bias there is ≈0. The bias only opens up once there is a full interval or more of exposure to the shifted, elevated-hazard region (h=4.0 onward) — ruling out "broken from the start" and pointing specifically at mechanism 2, scaling in with accumulated exposure to the shift.

**Deviation (user-approved 2026-09-27): the §7.5 rule stays failed-as-declared; `path_effect`'s implementation and this slice's plan are not changed.** `path_effect` faithfully reports an inherited property of the fitted forest's path-based cumulative-risk estimate (mechanisms 1-2 above), not a defect in its own delta-contrast logic, at the design's predeclared `delta=1.0` (a full-SD shift) and this sim's `n_train=1000`/200-tree scale. A one-line caution for users making large shifts into higher-hazard territory is added to `path_effect`'s docstring and `importance.rst` (below) as a direct consequence of this finding.
